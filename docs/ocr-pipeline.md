# OCR Pipeline

ConvertYard's image-to-text tools run entirely in the browser via Tesseract.js (all languages) and TrOCR via @huggingface/transformers (English handwriting, AI-Enhanced mode only).

## Pipeline overview

```
Input image
  → HEIC decode (heic2any, if needed)
  → PNG transparency composite (white background)
  → Preprocessing
      Standard path: preprocessForOcr() — grayscale → blur → perspective → CLAHE → Sauvola binarization → deskew → upscale
      AI path: preprocessForOcrDual() — same pipeline but returns { binary, grayscale }
  → OCR
      Standard: Tesseract.js (recognizePage) → OcrPageResult { text, words[], lines[], confidence }
      AI: detectLines() → cropLinesToBlobs() → TrOCR per line → { text, lines: TrOcrLineResult[] }
  → Word metadata collection (OcrWordMeta[])
  → Post-OCR correction (optional, English only)
  → Output file creation (text/md/csv/xlsx/json)
  → ConversionResult with ocrMeta attached (text-output modes only)
```

## Post-OCR correction

File: `lib/ocr/correction.ts` (pure functions) + `lib/ocr/correction.worker.ts` (dictionary loading)

### When it runs

Correction is applied after OCR when:
- `opts.autoCorrect === true` (UI toggle, default on)
- `lang === 'eng'` (English only — no multilingual dictionary)
- `mode` is `text`, `markdown`, or `combined`

Structured output modes (`receipt-csv`, `card-csv`, `table-csv`, `excel`, `json`) use separate field validators or no correction.

### Safety model

A word is a candidate for correction only when ALL conditions hold:
1. Engine confidence < 85 (high-confidence words are never touched)
2. Token is not in the dictionary as-is
3. Token is purely alphabetic after stripping edge punctuation
4. Token contains no digits, `@`, `/`, `#`, or `.`

### Confusion pairs

OCR engines make systematic errors from visual similarity. The correction engine uses this table:

| OCR reads | Likely intended |
|-----------|----------------|
| `rn` | `m` |
| `cl` | `d` |
| `li` | `h` |
| `vv` | `w` |
| `0` ↔ `O` | digit or letter |
| `1` ↔ `l` ↔ `I` | digit or letter |
| `5` ↔ `S` | digit or letter |
| `8` ↔ `B` | digit or letter |
| `ii` | `u` |
| `nn` | `m` |

Candidates are generated by applying confusion-pair substitutions to the input token. Only candidates found in the dictionary proceed.

### Ambiguity handling

If multiple dictionary candidates exist:
- Pick the highest-frequency one (SCOWL/frequency rank)
- If top two candidates are within 2× frequency of each other → no correction (ambiguous)

### TrOCR extra caution

TrOCR words carry `confidence: -1` (no beam-score available). For these, only candidates reachable by a single confusion-pair substitution are considered (stricter than Tesseract words).

### Structured mode field validators

For `receipt-csv` and `card-csv` only:
- `repairDigitTokens()`: substitutes O→0, l→1, S→5, B→8 inside tokens that already look numeric (prices, order numbers, phone digits)
- `repairEmail()`: fixes ` at ` → `@` flanked by valid local/domain parts; comma → period in TLD position

No dictionary correction is applied in structured modes — vendor names and personal names would be mangled.

### Dictionary

- Source: dwyl/english-words (~370k words), MIT license
- Asset: `/public/dicts/en.txt.gz` (gzip, ~1MB)
- Loading: lazy, on first correction request, in a Web Worker (`lib/ocr/correction.worker.ts`)
- Caching: in-memory for the session (built into the worker process)

## Word metadata (OcrWordMeta)

After OCR, each word is represented as:

```typescript
interface OcrWordMeta {
  text: string        // raw engine output
  corrected?: string  // only if correction changed it
  confidence: number  // 0–100 (Tesseract); -1 (TrOCR, unavailable)
  bbox?: { x0, y0, x1, y1 }  // omitted if > 5000 words (memory cap)
}
```

This metadata is attached to the `ConversionResult` for text-output modes:

```typescript
// Result variant for OCR text/markdown/combined modes:
{ file: File; ocrMeta: OcrResultMeta }

interface OcrResultMeta {
  kind: 'ocr'
  words: OcrWordMeta[]
  lines: string[]      // final line strings
  sourceIndex: number  // index into input files array
}
```

## Review panel data flow

1. `imageOcrConvert` returns `{ file, ocrMeta }` results (text-output modes)
2. `tool-shell.tsx` dispatcher handles the `ocrMeta` variant → stores on `FileEntry.ocrMeta`
3. In the `done` phase, `config.reviewPanel` is rendered with:
   - `files: File[]` — original input files
   - `results: ConversionResult[]` — reconstructed from entries (includes ocrMeta)
   - `onResultEdit(index, newFile)` — replaces `entries[index].result` via `EDIT_RESULT` action
4. User edits text in `OcrReviewPanel`, clicks "Apply changes" → `onResultEdit` called
5. `EDIT_RESULT` updates the entry's result file
6. Downloads (single and ZIP) use the updated result file
